# Plan 014: Preview Panel for Rendered Content in the Chat

**Spec:** `docs/specs/014-preview-panel.md` (Approved 2026-11-03)
**Architecture:** Modular Monolith; this spec is client-only (`Quorum.Web.Client`) plus one static-file response-header rule in the Host. No module, endpoint, entity or migration is touched.
**Mode:** tests per acceptance criterion where they can run (bUnit for components, pure C# for the render rules, Host integration for the served policy and assets); the isolation criteria (AC-21 to AC-27) are verified with a recorded browser check, as the spec's deferred decision on Playwright prescribes.
**Status:** Draft
**Affected:** `Quorum.Web.Client` (`MarkdownRenderer`, `Pages/Chat.razor`, new `Components/PreviewPanel.razor` and preview state classes, `wwwroot/preview.js`, `wwwroot/preview/**`, `wwwroot/css/app.css`, `wwwroot/index.html`), `Quorum.Host` (`Infrastructure/PreviewSecurityHeaders.cs`, `Program.cs` wiring), `scripts/`, `tests/Quorum.Integration.Tests` (`Web/`, `Host/`), `docs/checks/`.

## Decisions

| Topic | Choice |
|---|---|
| Preview button markup (D-23, AC-1 to AC-5) | A custom Markdig object renderer for fenced code blocks, registered in `MarkdownRenderer`. Recognised info strings (`html`, `htm`, `svg`, `json`, `csv`, `mermaid`, `mmd`, case-insensitive; aliases folded) wrap the usual `<pre><code>` in a toolbar `div` with a `<button type="button" class="preview-open" data-preview-kind="…">Preview</button>`. The text never goes in an attribute; raw HTML stays disabled and nothing else of the pipeline changes. The rules live in a small pure class (`PreviewKinds`) so they are unit-testable without a DOM. |
| Closed blocks only (D-2, AC-3) | Markdig does not record whether a fence was closed, so a source-level scanner (`FenceScanner`, pure C#) reports whether the last fenced block of a markdown string is still open. `MarkdownRenderer.ToHtml` gains an optional `streaming` flag: when set and the last block is open, that block gets no button. `Chat.razor` passes the flag only for `run.Partial`; stored messages are always rendered closed. |
| Opening the panel (D-23) | One delegated `click` listener bound to the messages container in a new `wwwroot/preview.js` (host-side glue, loaded from `index.html` next to `chat.js`). It reads `data-preview-kind` and the block's `textContent`, remembers the clicked button (focus return, AC-9) and calls `[JSInvokable] OpenPreview(kind, text)` on the page's existing `DotNetObjectReference`. The listener survives Blazor re-rendering the bubbles because it is bound to the stable container. |
| Panel component (D-3, D-4, D-20, D-21) | `Components/PreviewPanel.razor` (MudBlazor chrome) rendered by `Chat.razor` inside `.chat-layout` as a third flex area. The content descriptor is `PreviewContent` (`Kind`, `Text`, optional `Title`); the panel owns the per-preview switch state itself and the page owns one nullable `PreviewContent`: it drops it when the conversation `Id` changes or the page disposes, and keeps it across sends, regenerations and scrolling. Bar: kind + size title, Copy, Download, the two HTML switches, a menu with "Ask before running scripts" / "Ask before loading remote images", X. `role="complementary"` with a label, Esc closes while the focus is inside, focus moves in on open and back to the opener on close. Below 960 px a media query turns the same panel into a full-screen overlay with a back button (the drawer pattern of spec 010); at ≥960 px the width is a CSS variable set by a pointer-drag handle in `preview.js`, clamped to [320 px, 70%] and persisted. |
| Viewer (D-6 to D-9) | A static page `wwwroot/preview/viewer.html` with its script `wwwroot/preview/viewer.js`, embedded as `<iframe src="preview/viewer.html" sandbox="allow-scripts" title="…">` created only while the panel is open (AC-35). No `allow` permissions attribute. Host ⇄ viewer protocol as the spec's table plus one addition: `render`/`theme` in, `ready`/`rendered`/`error`/`escape` out (`escape` carries D-3's "Esc while the focus is inside the viewer": a keydown there never reaches the page, so the viewer forwards it); both sides check `event.source` (host: the iframe's `contentWindow`; viewer: `window.parent`) and ignore everything else (D-8, AC-27). Text always travels as a string and is only ever inserted via `textContent`, `srcdoc` or a data URI, never evaluated. |
| CSP delivery (D-7 — mechanism is a plan detail) | A sandboxed frame without `allow-same-origin` has an opaque origin, so `script-src 'self'` in the viewer would match nothing and the vendored libraries could not load. The policy is therefore sent as a **response header** on `/preview/**`, stamped by a small `PreviewSecurityHeaders` rule in the Host's static-file pipeline using the request's own origin: `default-src 'none'; script-src {origin}/preview/; style-src 'unsafe-inline'; img-src data:; font-src data:; form-action 'none'; base-uri 'none'; frame-src about:`. No `connect-src`, so the viewer cannot fetch; `frame-src about:` covers the nested `srcdoc` frame and blocks its navigation (D-7, AC-23). Everything under `/preview/` is the app's own vendored content, which is what D-7 allows. `viewer.html` carries **no** `<meta>` policy: a meta CSP cannot name the request's origin, and whatever it could express would only intersect with the header policy and break the vendored scripts. The header is the single barrier; the Host integration test pins it. |
| HTML and SVG renderers (D-9, AC-18, AC-19) | HTML: the viewer builds a nested `<iframe srcdoc sandbox="">` (or `sandbox="allow-scripts"` with Run scripts on); the srcdoc starts with a `<meta http-equiv="Content-Security-Policy">` allowing only inline styles and `data:` images/fonts (`form-action 'none'`, `base-uri 'none'`; `script-src 'unsafe-inline'` added only with Run scripts; `img-src` extended with `https:` only with Load remote images), then a white-canvas style, then the block's text verbatim. The frame is recreated whenever an option changes. A content-supplied looser meta policy can only intersect, never widen (AC-26). SVG: `<img src="data:image/svg+xml,…">` (percent-encoded), which runs no script and loads nothing external. |
| JSON (D-11, AC-14, AC-15) | Vendored `json-formatter-js` (MIT), classic UMD script, root expanded one level, values as text. `JSON.parse` runs first; a failure sends `error` `{code:"parse"}` with the library message and position, and the panel keeps Copy and Download. |
| CSV (D-12, AC-16) | Hand-written RFC 4180 parser in `viewer.js` (quoted fields, doubled quotes, newlines inside quotes); delimiter is the most frequent of `,` `;` tab on the first line; first row is the header; the table is built with `textContent` only, sticky header, horizontal scroll, ragged rows as they are. Above 5,000 rows the viewer sends `error` `{code:"limit"}` (D-16, AC-32). |
| Mermaid (D-13, AC-17, AC-34) | Vendored `mermaid` v12.3.0 (MIT), classic script `dist/mermaid.min.js` (an IIFE exposing `globalThis.mermaid`), loaded by injecting a script tag on the first Mermaid render only (the `editor.js` pattern). `mermaid.initialize({ securityLevel: "strict", htmlLabels: false, theme })` with the theme from the host colours; render errors go back as `error` `{code:"parse"}` with the library message; a `Promise.race` abandons a render after 10 s with `{code:"timeout"}`. The renderer code ships in `viewer.js` with PR 1; the vendored library itself arrives in PR 2, so until then a Mermaid preview fails into the library-error path ("The preview could not start" with Retry). The pin lives in `scripts/vendor-preview-libs.ps1`; upgrading is a rerun of the script. |
| Theme (D-14, AC-12) | `preview.js` reads the computed values of a fixed list of `--mud-palette-*` variables and sends them with `render` and on every `ThemeState.Changed` while the panel is open. HTML and SVG keep their white canvas regardless. |
| Consent (D-17, D-18, AC-28 to AC-31) | Two MudBlazor dialogs with a "Don't ask me again" box, worded as the spec says. Choices and the panel width live in `localStorage` under keys scoped to the signed-in user (`quorum.preview.<email>.runScripts.dontAsk`, `.remoteImages.dontAsk`, `.width`), read and written through `preview.js` inside try/catch so an unavailable `localStorage` degrades to asking every time (AC-31). Both switches reset to off when another preview replaces the content, unless the stored choice says otherwise. The panel menu entries remove the stored choices. |
| Copy, Download (D-4, AC-20) | `navigator.clipboard.writeText` with the raw text; download builds a local `Blob` and clicks a transient `a[download="preview.<ext>"]` (`html`, `svg`, `json`, `csv`, `mmd`) — no request. |
| Limits and failures (D-16, D-19, AC-32, AC-33) | The 1 MB text cap is enforced host-side (`PreviewRules.MaxTextBytes`, counted in UTF-8 bytes) before any render message: the panel opens straight into the limit notice with Copy and Download. The viewer gets a 5 s `ready` timer per creation; on timeout or a library load failure the panel shows "The preview could not start" with Retry (recreates the iframe), Copy and Download. Renderer errors arrive as `error` messages and are shown in the panel body, never as an app exception. |
| Vendoring (D-15, AC-37) | `wwwroot/preview/lib/json-formatter-js/{json-formatter.umd.js,json-formatter.css,LICENSE}` and `wwwroot/preview/lib/mermaid/{mermaid.min.js,LICENSE}` (PR 2) plus `wwwroot/preview/lib/VENDORED.md` listing version and SHA-256 of every file. A `scripts/vendor-preview-libs.ps1` downloads them from pinned jsdelivr URLs and writes the note, so upgrading is a rerun of the script. Nothing in the viewer or the panel references an external address. |

## Verification

Per PR: `dotnet build`, `dotnet test` (Docker for Testcontainers), `dotnet format --verify-no-changes`, `get_diagnostics`, and the browser check for the ACs that only a browser can prove. PR 2 closes the plan and flips its status.

## Risks

- **Opaque origin vs CSP**: `script-src 'self'` does not work inside `sandbox="allow-scripts"` without `allow-same-origin`; the origin-stamped header is the workaround. If a browser disagrees, the fallback is a sha256-hashed inline bootstrap in `viewer.html` that imports the libraries — recorded in the browser check before PR 1 merges.
- **Vendoring needs network access once** (jsdelivr). If the sandbox blocks it, the files are fetched by the developer and the script only verifies hashes.
- **Mermaid in git** adds a few MB to the repo — accepted by D-15; only `mermaid.min.js` is committed, not the full dist.
- **Markdig renderer override** must not change any existing output beyond the toolbar: the current markdown tests are the regression net, plus AC-5.
- **bUnit cannot prove isolation**: the security ACs rest on the recorded browser check across Chromium, Firefox and Safari; the checklist is part of PR 1 so it cannot be forgotten.
