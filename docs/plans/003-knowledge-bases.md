# Plan 003: Knowledge Bases

**Spec:** `docs/specs/003-knowledge-bases.md` (Approved 2026-10-17)
**Architecture:** Modular Monolith; Vertical Slice inside each module.
**Mode:** `/tdd`: every acceptance criterion becomes a failing test first.
**Status:** Approved (2026-10-17)

## Decisions
| Topic | Choice |
|---|---|
| Tool origins | `ToolOrigin` is `Builtin` (ships with Quorum, fixed catalog, same for every tenant), `Mcp` (discovered from a server) and `Rag` (configured by an admin over knowledge bases). `Native` is renamed `Builtin` before the rag tool is added, because the rag tool is also in-process code and the old name no longer tells the origins apart. Everything named after it follows: `INativeTool` → `IBuiltinTool`, `NativeToolCatalog`, `NativeToolProvisioner`, `NativeToolsInitializer`, `NativeQuorumTool`, the exposed prefix `native__` → `builtin__`, the stored value `Native` → `Builtin`, the `origin` of `GET /tools` and the Web client models. The tool name the model sees is not stored with conversations, and the audit log keeps names without prefix, so no history needs migrating; only the rows of `agents.tools` do. Spec 004 gets an amendment note rather than a rewrite |
| Ownership | A new module **KnowledgeBases** (`Quorum.Modules.KnowledgeBases` + `.Contracts`, schema `knowledge_base`) owns dictionary, KB registrations, the Qdrant connector, discovery and search. The **rag tool** is a tool of origin `Rag` in **Agents** (pool, activation, policy, audit and the loop are there). **Conversations** stores and returns the sources of a message and relays the new SSE event. Nobody reads another module's tables |
| Contracts between modules | `KnowledgeBases.Contracts`: `IKnowledgeBaseSearch` (search the given KBs for a tenant and assistant) and `IKnowledgeBaseCatalog` (describe the visible KBs and fields of a binding; check that a binding's KBs and fields are visible to a whole scope). `Agents.Contracts` gains `IEmbeddings` (KnowledgeBases embeds a text with a named model on the tenant's endpoint) and `IRagToolUsage` (which rag tools use a dictionary field, for `knowledge_base.field_in_use` and `usedByCount`). Contracts reference only `Quorum.Shared` (the architecture test already enforces it); the two Contracts projects do not reference each other. No Microsoft.Extensions.AI type crosses a Contracts project |
| Permission | `QuorumPolicies.KnowledgeBaseManage = "knowledge_base.manage"`, registered in `TenancyModule` next to the tool policies (`Admin` today). Rag tool endpoints use `tools.manage` / `tools.attach` / `tools.use` |
| Qdrant access | The official **`Qdrant.Client`** (gRPC, port 6334), not an own REST client and not `Microsoft.Extensions.VectorData` (typed records do not fit a payload chosen by the admin). The client has no hook for the transport, so `QdrantConnector` builds the `GrpcChannel` itself over the named guarded `HttpClient` (`knowledge-base-qdrant`) and adds the `api-key` header with a small interceptor; it turns payloads into JSON for the mapping and failures into a few outcomes (blocked, unreachable, unauthorized, not found, unexpected). The URL the admin pastes is the gRPC one; the verification message says so when the REST port is used. Calls: collection info (vectors, distance, payload indexes), scroll (sampling, payload only), health (version), and the query API for search in PR 4 (Qdrant 1.10 or later) |
| URL guard | `McpUrlGuard` and `IMcpHostResolver` move to `Quorum.Shared` as `OutboundUrlGuard` / `IHostResolver` (infrastructure, no business logic) and Agents keeps using them; the Qdrant `HttpClient` (`knowledge-base-qdrant`) has the same handler settings: no redirects, no system proxy, `ConnectCallback` that validates the address the socket opens, request logging removed. The existing `McpUrlGuardTests` keep passing unchanged |
| Secrets | `KnowledgeBaseSecretProtector` (own purpose string `Quorum.KnowledgeBase.Connection`) encrypts the API key with Data Protection; the API returns `hasApiKey` only. The connection is stored as kind-specific JSON (`Url`, `Collection`, `VectorName`, protected `ApiKey`) |
| Embeddings | `OpenAiEmbeddings` in Agents implements `IEmbeddings` with an own small client in the style of `OpenAiChatClient` (`POST {baseUrl}/embeddings`, the tenant's model endpoint and key, one input per call, the model name given by the KB). An endpoint without `/embeddings` or a model that is not served gives a clear error. The result is validated as a non-empty vector of finite numbers |
| Mapping model | `Mapping` is owned JSON on the KB: `Roles { Text, DocumentId?, Title?, Position?, SourceUrl? }` (payload paths, dot notation) and `Fields [{ Path, DictionaryFieldId }]`. `MappingConventions` (role names, metadata naming) and `PayloadSampler` (type inference) produce the draft; `JsonSchemaReader` produces the same draft from a pasted schema (it first checks the schema against the meta-schema of its draft with JsonSchema.Net, and walks the properties itself: the library validates and has no API to list properties with types). One draft model, three sources, so the review screen is the same |
| Visibility | `KnowledgeBaseVisibility` and `DictionaryVisibility` are the only queries that turn the tenant filter off, like `ToolVisibility`: own rows, `Global`, listed `Tenant`, and `Assistant` only for the owner's assistants. Another tenant's view of a shared KB is a reduced DTO without URL, collection or key |
| Generated tool definition | `RagToolDefinition` builds the description and the JSON Schema of a rag tool from its binding and `IKnowledgeBaseCatalog` **at the start of each answer**, not at save time, so a renamed or deleted KB never leaves a stale enum. `Tool.InputSchema` holds `{}` for rag tools; `ActiveToolsQuery` hands the stored rows to a `RagToolResolver` in `AssistantChat.PrepareAsync` that replaces description and schema, drops rag tools left with no visible KB and returns the result to the existing `QuorumToolFactory`. The admin preview endpoint uses the same builder, so what the admin sees is what the budget counts |
| Call-time check | `Tool.DefinitionHash` of a rag tool is the SHA-256 of its stored configuration (KBs, exposed fields, fixed filters, limits, scope). The existing check in `ToolCallInvoker` ("the hash I was offered is still the stored one") then refuses a call after an admin changed the binding mid-answer. The search itself re-validates against the live catalog |
| Filter parameters | Built from the exposed fields: text → `<field>: string[]`; number → `<field>_min`, `<field>_max`; date → `<field>_from`, `<field>_to` (ISO 8601 date); boolean → `<field>: boolean`; list → `<field>: string[]`. Descriptions come from the dictionary. Fixed filters use the same shapes in `FixedFilters` JSON. `FilterTranslator` turns them into one Qdrant `must` list per KB using each KB's mapped payload paths; a KB lacking a mapped path for any filter is skipped (D-12). Limits: at most 20 values per list, 200 characters per value |
| Search engine | `KnowledgeBaseSearch`: resolve the visible KBs of the binding → embed once per distinct (model, prefix) → query each KB in parallel under one 15 s token → keep scores per KB, drop below the threshold → interleave round-robin in KB-name order → cut whole chunks to the character cap → map payload to roles. Per-KB failures become notes; `Status` is updated on each search (`Unavailable` on failure, `Available` on success) with a single-row `ExecuteUpdate`, never loading the entity |
| Tool output | `RagQuorumTool` renders the result as numbered blocks (`[n] KB · title, position`, then the chunk inside a per-request delimiter and the data label of spec 002, reusing the delimiter generator of `AttachmentBlock`), then notes (skipped KBs, failed KBs, "nothing found"). The numbers come from a per-answer `SourceNumbering` that the factory hands to every rag tool of the answer |
| Sources | `QuorumTool` gets a virtual `RunWithSourcesAsync` returning `ToolOutput(Text, Sources)`, defaulting to `RunAsync`; the invoker publishes a `Sources` chunk (`AnswerChunkKind.Sources`, `SourcesEvent`) before the `ToolResult` chunk. Conversations collects them in `AnswerStream`, stores them as `MessageSource` rows with the assistant message and sends `sources` over SSE live |
| Audit | `ToolAuditEntry` gains a nullable `SourceCount` (migration in PR 5). Arguments, redaction, fail-closed and retention are untouched. The search text and chunks never reach the audit log |
| Test infrastructure | `Testcontainers` Qdrant (the `Testcontainers.Qdrant` package, or a generic container if it does not fit) beside the existing `PostgresFixture`. `FakeModelServer` learns `/embeddings`. `tools/Quorum.SampleKnowledgeBase` (a library plus a small console tool) builds the sample collections of D-20 with a **deterministic embedding** (hashed bag of words into 64 dimensions, normalised) so that tests can assert real ranking without a model; the integration tests reference the library. Time-dependent paths use `FakeTimeProvider` |
| UI | Existing MudBlazor components and the `ToolAdminView` style (logic in plain classes, covered by bUnit). Admin: a "Knowledge" area with the dictionary, the knowledge bases (guided registration, verify, test search) and, in the Tools page, the rag tool editor with the definition preview. Chat: a `SourcesList` under the answer |

Findings of the step 8 prototype (Qdrant v1.12.0, the image of the dev compose; made over REST, the server's behaviour is the same over gRPC), which PR 4 builds on:
- `GET /collections/{name}`: `result.config.params.vectors` is `{ size, distance }` for one unnamed vector and `{ <name>: { size, distance } }` for named ones; `result.payload_schema` maps every indexed payload path (nested ones in dot notation, `meta.year`) to `{ data_type, points }`; `points_count` is there. A missing collection is HTTP 404. Errors are `{ "status": { "error": "..." } }`.
- `POST .../points/scroll` with `limit`, `with_payload: true`, `with_vector: false` returns `result.points[].payload`.
- `POST .../points/query` takes the vector as `query`, `using` for a named vector (required whenever the collection has named vectors, also when there is only one), `filter`, `limit`, `score_threshold`, and `with_payload` as `true`, `false` or a list of paths. Without `using` on a named collection, or with a wrong vector size, it answers 400 with the cause in `status.error` (`expected dim: 128, got 64`).
- Filters: `match.any` for texts and lists of texts, `match.value` for booleans, `range.gte/lte` for numbers, and nested paths in dot notation all work. **Date ranges work with ISO 8601 strings in `range` (date-only included), with or without a datetime payload index**: there is no separate `datetime_range` key (it is rejected). An index only makes it faster.
- `GET /` returns `{ version }`: the version check reads it, and tolerates a proxy that hides the root.

Decisions taken while building PR 4 (details the spec leaves open):
- **Contracts.** `IKnowledgeBaseSearch.SearchAsync(KnowledgeBaseSearchRequest)` takes tenant, assistant, the KB ids already chosen by the caller (the rag tool narrows to the `knowledge_base` the model named), the query, the model's filters and the binding's fixed filters (both as the flat parameter objects of D-11, `JsonElement` values), top K, threshold and cap. It returns chunks (KB name, score, text, document id, title, position, URL), the names of skipped KBs, the failed KBs (name, code, safe message), the number of unusable chunks and whether the first chunk alone exceeded the cap; the result is an error when nothing could be searched (`knowledge_base.filter_unsupported` when every KB was skipped, `knowledge_base.unavailable` when every searched KB failed, `knowledge_base.not_found` when no KB is visible or the tenant is not the request's). `IKnowledgeBaseCatalog` has `DescribeAsync` (KBs with their description and mapped visible fields, plus any extra fields asked for) and `CheckScopeAsync` (which KBs and fields are not visible to the whole scope of a binding; `ScopeVisibility` holds the rule).
- **Filters.** Model and fixed filters both apply (AND), so the model can only narrow a fixed filter. A `null`, an empty list or an empty string from the model is no filter; a bare string is a list of one. A fixed filter that does not fit is `knowledge_base.invalid_fixed_filter` with a message that does not say what is in it. A date given without a time as the end (`_to`) covers that whole day.
- **Dates over gRPC.** The REST `range` on ISO strings of the prototype becomes `datetime_range` with timestamps in gRPC; verified with and without a datetime index, and on date-only payload strings.
- **Threshold.** It is passed to Qdrant, which knows whether a higher or a lower score is better for the collection's distance; the search does not filter again.
- **Status.** A search updates the status only of KBs owned by the searching tenant: a failure of another tenant's embedding endpoint must not mark a shared KB unavailable for its owner.
- **Test search.** `POST /knowledge-bases/{id}/search` works on the administrator's own KBs (the tenant filter keeps shared ones out); no threshold and no character cap, `limit` 1 to 20 (default 5).
- **Limits.** A query has at most 2,000 characters. Source references from a payload are cut to 300 characters; a URL over 2,000 characters is dropped, not cut. A reference of the wrong type leaves that reference empty; only a missing or non-text `text` makes a chunk unusable.

Decisions taken while building PR 5 (details the spec leaves open):
- **Storage.** The binding is `agents.rag_tools`, one row per tool keyed by the tool id (cascade on delete): knowledge base ids, exposed field ids, fixed filters as `jsonb`, limits and scope. `FixedFilterFieldIds` keeps the fields the fixed filters name, so that a field used only by a fixed filter is still "in use" (`IRagToolUsage` returns exposed and fixed-filter fields together). The tool row is `Tool` with origin `Rag`, `InputSchema` `{}`, state `Enabled` and policy `Auto` unless the request says `Confirm`; `DefinitionHash` is the hash of the whole configuration, name and description included (`RagToolHash`, sorted ids and canonical JSON, so the order an administrator listed things in does not matter).
- **Names.** Up to 40 characters, `[a-z0-9][a-z0-9_-]*` (exposed as `rag__<name>`, at most 45 of the 64 the model APIs allow). The unique index on built-in tools is now per origin, so a rag tool may share a name with a built-in one (their exposed names differ). The audit log records a rag call with server name `rag`, which is what makes the `tool=rag__name` filter work like `server__tool`; `rag` joins `builtin` among the names an MCP server cannot take.
- **Generated definition.** The description is the administrator's text followed by the visible knowledge bases with their descriptions; the schema has `query`, `knowledge_base` (only with more than one visible knowledge base) and the parameters of the exposed fields that at least one visible knowledge base maps. `additionalProperties` is `false`, so an unknown parameter is an invalid-arguments result before anything runs. `RagToolResolver` builds it for an answer (`AssistantChat.PrepareAsync`), for the pool listing (so the size counted by the warnings is the real one) and for the preview, with one catalog call per batch of tools.
- **Pool.** `ToolPool` applies the scope of the binding (Global, Tenant with the owner or the listed tenants, Assistant for the owner's listed assistants); that a rag tool has a visible knowledge base needs the catalog, so `GET /assistants/{id}/tools` and `PUT /assistants/{id}/tools` apply it afterwards (`tool.not_in_pool` for an activation) and the answer drops such a tool. Tools of other tenants appear in `GET /tools/rag` flagged `shared`, without knowledge bases or scope lists; reading, editing and deleting them is 404.
- **Validation order and codes.** Name, description, policy, knowledge base count, exposed field count, limits, scope shape and assistants (the codes of spec 004: `tool.invalid_scope`, `tool.scope_not_supported`), visibility of the knowledge bases, exposed fields among the fields the knowledge bases map, fixed filters, and the rule between scopes. Codes besides the spec's: `rag.no_knowledge_base`, `rag.invalid_description`, `rag.invalid_policy`, `rag.not_found`. An exposed field no knowledge base maps and a fixed filter that is wrong are `rag.invalid_filter`; a knowledge base or field the scope cannot see (or that does not exist) is `rag.knowledge_base_not_visible`. Limits: result size 200 to 50,000 characters (default 6,000), results 1 to 20 (default 5).
- **Fixed filters.** Checked at save with the parser the search uses (`IKnowledgeBaseCatalog.CheckFixedFiltersAsync`, new): same shapes and caps as the model's filters, but an empty value is refused, because a fixed filter that restricts nothing would widen access. They may name any field the knowledge bases map, exposed or not.
- **Result.** `RagResultFormat` renders a notice that the text is data, then `[n] knowledge base · title, position` and the chunk between `<<<SOURCE-delimiter>>>` markers (the delimiter is random per call and removed from the text if it appears there), then the notes: knowledge bases skipped for a filter, knowledge bases that failed, chunks without text, "nothing was found" or "the best match is larger than the result size limit". Errors of the search reach the model with the description the search wrote (it carries no address, key or internal detail). A tool may now return its sources: `QuorumTool.RunWithSourcesAsync` returns `ToolOutput(Text, Sources)`; this PR audits `Sources.Count` (`SourceCount`, also in `GET /tools/audit`), PR 6 publishes them.
- **Audit arguments.** The query is part of the audited arguments as for any tool (spec 004 D-12, D-21); the chunks are never audited, only their number.
- **Deleting a dictionary field** is checked against knowledge bases under the lock a knowledge base takes to save its mapping, and against rag tools without it (they live in another schema): a tool saved in the instant a field is deleted would name a field that no longer exists, which the catalog hides and the tool ignores; the resolver logs a warning with the tool id and the number of missing fields (ids and counts only), so the occurrence is not silent. A result is also kept within the tenant's limit on tool results: refused at save when the size plus the formatting (500 characters and 300 per source) cannot fit, and reduced at call time if the limit was lowered afterwards. The gauge of the context (not an answer) may reuse a rag definition made in the last 30 seconds.
- **Assistant ids in a scope** (step 22) go through `IAssistantDirectory.MissingAsync`; a knowledge base with an assistant scope that names an unknown assistant is `knowledge_base.invalid_scope`.

### PR 6 - Citations (`feat/003-citations`)
22. `AnswerChunkKind.Sources`, `AnswerSource`, `SourcesEvent` in `Agents.Contracts`; `QuorumTool.RunWithSourcesAsync`; the invoker publishes `Sources` before `ToolResult`; numbering continues across calls in one answer. AC-37.
23. Conversations: `MessageSource` entity and migration; `AnswerStream` relays the `sources` event and stores the sources with the message (only references: KB name, document id, title, position, URL); `GET /conversations/{id}` returns `sources[]`; regeneration replaces them; deleting the conversation or message deletes them; a deleted KB leaves the stored copy untouched. AC-38, AC-39, AC-41.

Decisions taken while building PR 6 (details the spec leaves open):
- **Numbering was already done.** `RagResultFormat` numbers the sources with the per-answer `SourceNumbering` and `QuorumTool.RunWithSourcesAsync` exists since PR 5; this PR adds the contract types and the publishing. `AnswerSource` and `SourcesEvent(CallId, Sources)` are in `Agents.Contracts`; the invoker publishes a `Sources` chunk just before the `ToolResult` of the same call, and only for a call that succeeded with at least one source (nothing found, a failed call, a result over the limit, or a denied call publish none, and a result over the limit also gives its numbers back).
- **SSE.** The event is `sources` with `{ sources: [{ n, knowledgeBase, documentId, title, position, url }] }` as in the spec, without the call id. The Web client already ignores event types it does not know, so the stream is safe for it before PR 8.
- **Storage.** `conversations.message_sources` (migration `AddMessageSources`): one row per source, `MessageId` with cascade delete, tenant query filter, the knowledge base by name (not id, so a rename or a deletion leaves the copy as it was), document id, title and position up to 300 characters, URL up to 2,000 (a URL that does not fit is dropped, as in the search). Chunk text is never stored. Sources are stored with the message whatever its final status (an interrupted or failed answer keeps those it had received, the text it cites may be there).
- **Replacement and deletion** are the database cascade: regeneration already deletes the replaced message and deleting a conversation already deletes its messages, so no code of its own and no message-level delete endpoint (there is none).
- **GET.** `sources[]` on every message, ordered by `n`; empty for user messages and for answers that cited nothing.

### PR 7 - Admin UI (`feat/003-ui-admin`)

25. Decisions taken while building PR 7 (details the spec leaves open):
- **Where.** `/knowledge` (the knowledge bases and the guided registration) and `/knowledge/dictionary`, with a "Knowledge" entry in the top bar next to "Tools" (admin only, like Tools). The rag tool editor is a component (`RagToolsSection`) of the Tools page. The logic lives in plain classes covered by tests, as for `ToolAdminView`: `KnowledgeBaseDraft` (connection, schema, scope and the request), `MappingDraft` (the rows under review), `FilterInputs`, `RagToolForm` / `RagToolView`, `ScopeForm`.
- **Registration.** Connection → inspection (findings, warnings by level, unindexed fields, vector choice, optional pasted schema sent as text) → mapping → scope → save. Editing uses the same steps, starting from the saved mapping ("Keep the mapping" skips the inspection; inspecting again replaces the mapping with a new draft). An unreachable store or a missing collection shows the inspection and does not offer the mapping.
- **Mapping rows** are bound to the dictionary by name: an existing name reuses the field (sent by id), a name that is not there is a new field of the type the payload suggests (changeable) and is created only when the admin ticks the confirmation (`createFields`). A clash of names, an invalid or reserved name, a path mapped twice and a type conflict with the dictionary block the step; a conflict is resolved by renaming or by accepting the dictionary's type. The checks repeat the server's to save a round trip, the server decides.
- **Rag editor.** The fields offered are those the selected knowledge bases map, read from their detail; selecting a knowledge base exposes its new fields up to 10 (D-11), and a field the admin removed stays removed. A knowledge base of another tenant does not show its mapping, so every dictionary field is offered and the server refuses the ones nobody maps. Fixed filters are added per field with the shapes of D-11 (texts split on commas, so a value cannot contain one) and a filter with no value is refused. There is no preview endpoint for an unsaved tool: the editor shows a local list of the parameters while editing and, after each save, stays open on the saved tool with the definition the server generates and its estimated size.
- **State and policy** of a rag tool are changed in the list like those of any tool (`PUT /tools/{id}`, the same row component); the editor also sets the policy when saving.
- **Test search** offers a filter input for each mapped field; a result link is rendered only for `http` and `https`, with `rel="noopener noreferrer"`.

### PR 7b - Clusters and aliases (`feat/003-clusters`)

### PR 8 - Sources in the chat (`feat/003-ui-chat`)
26. `SourcesList` under the answer, `[n]` markers matching, cited sources first and the others collapsed, links only for `http` and `https` with `rel="noopener noreferrer"`, text never as HTML; sources come back when the conversation is reopened. AC-40, AC-50.

Decisions taken while building PR 8 (details the spec leaves open):
- **Cited or not** is read from the answer's text: a `[n]` marker, or several in one (`[1, 2]`, `[1][2]`), cites source `n`. Cited sources are listed first under "Sources"; the others sit in a collapsed "Other sources (n)" (just "Sources (n)" when the text cites none). The text itself is not rewritten: the `[n]` label in front of each entry is what a marker matches, and nothing in the markdown renderer changes.
- **While it streams** the list grows with each `sources` event, in the order the sources arrive and grouped by document, and nothing is split or moved: the text is not finished, so what it cites is not known. When the answer ends the conversation is reloaded and the stored sources replace it, now split into those the text cites and the others, collapsed; a regeneration starts from an empty list.
- **Rendering.** The logic is a plain class (`SourcesView`) covered by tests; `SourcesList`, `SourceEntry` and `DocumentName` only draw it. Sources are grouped by document (knowledge base, document id and title) with its places under it. A document cited once as a whole (no position) fits on one line with its number. Otherwise the document is the heading and each place is a line under it with its number and `Section: <position>` (`Page: <n>` when the position is a bare number). A title falls back to the document id and then to "Source n"; sources with neither are never grouped together. The heading carries the knowledge base name and, only when there is no link and the id is not already the label, `File: <document id>`. A link is made only for an absolute `http` or `https` address, with `target="_blank"` and `rel="noopener noreferrer"`: on the document when all its places share one address, on each place when they differ (anchors to a section); every other value (relative, `javascript:`, `data:`, `file:`) is shown as text, and nothing from a source is ever rendered as markup.
- **One number for one source.** A model may search twice and get the same passage back. `SourceNumbering` now keys a source by knowledge base, document id, title, position and URL: a source found again keeps its number, the result the model reads shows it under that number, and only the sources numbered for the first time are published and stored (so the unique `(MessageId, N)` holds). The audit's `SourceCount` is the number of distinct sources of the result, new or not; a discarded result gives back only the numbers it took. This refines AC-37, which says numbering continues across calls: it does, for new sources. Two different chunks with the same position in one document share a number, as they are the same place for the reader. The client still merges one place stored under several numbers (answers stored before this change), so every marker finds its entry.

## Risks
- **Retrieval quality on small models**: the model may not call the tool, filter wrongly or ignore the sources. Mitigation: a short generated definition, admin-chosen exposed fields, errors that name what to fix, the `[n]` instruction; quality is observed in step 28.
- **Qdrant API differences across versions**: `points/query` needs 1.10 or later; response shapes and datetime filters changed over versions. Mitigation: the prototype in step 8, a version check in verification, tests against the pinned image of the dev compose.
- **Ingestion and retrieval models differ** (dimension, prefix, normalisation): the worst failure is silent bad ranking. Mitigation: the dimension check, the optional prefix, the admin test search with visible scores, and the data-owner documentation. A model of the same size but different space cannot be detected.
- **Payloads vary**: 20 sampled points may miss optional fields or show mixed types. Mitigation: the review step lets the admin add and edit mappings by hand; mixed types default to text with a warning.
- **Unindexed filter fields on large collections** are slow. Mitigation: `unindexedFields` warning at inspect, documented; no automatic index creation (Quorum never writes to the store).
- **Cross-tenant leaks through shared KBs**: the visibility queries are the only place that disable the tenant filter. Mitigation: a dedicated test per rule (own, Global, Tenant list, Assistant), the reduced DTO, and the search taking tenant and assistant explicitly and refusing a tenant that is not the ambient one.
- **Prompt injection through retrieved chunks**: delimiters with a per-request token, the data label, policies and confirmation of other tools unchanged (spec 004 D-31); a hostile chunk cannot call a tool that needs confirmation without the user seeing the arguments.
- **Context budget**: the generated definition counts in the tools segment and a result is capped at 6,000 characters by default; the admin ceilings keep a result from filling the context. The preview shows the size.
- **Search latency**: embedding plus Qdrant on each call, under the 15 s limit and the tool-call timeout of spec 004 (30 s), whichever is shorter. A slow embedding model makes every question slow; documented, measured in step 28.
- **Three modules, three migrations** (`knowledge_base`, `agents`, `conversations`) across PRs: review them in order and keep each reversible.
- **Moving the URL guard to Shared** touches a security component. Mitigation: a mechanical move, the existing guard tests unchanged, done in its own early step.
- **Hosted background answer and the tenant context**: the answer runs on a background task but in the request's scope; the search receives tenant and assistant as arguments and the test covers a tenant mismatch.

## Details beyond the spec to confirm
- Qdrant is reached with the official `Qdrant.Client` over gRPC (port 6334), minimum Qdrant 1.10; no `Microsoft.Extensions.VectorData` (reason in Decisions). Changed from an own REST adapter on review: prefer established libraries.
- `McpUrlGuard` and its resolver move to `Quorum.Shared` as `OutboundUrlGuard`.
- `Agents.Contracts` gains `IEmbeddings` and `IRagToolUsage`; `KnowledgeBases.Contracts` has `IKnowledgeBaseSearch` and `IKnowledgeBaseCatalog`.
- The rag definition is built at the start of each answer from the live catalog, and `Tool.DefinitionHash` is the hash of the stored configuration.
- Scope in the API is the object `scope: { kind, tenantIds?, assistantIds? }` for dictionary fields (`Global` / `Tenant`), KBs and rag tools, with the validation rules of spec 004 (`Global` takes no ids, `Tenant` lists tenants besides the owner, `Assistant` lists existing assistants of the owner); extra codes `knowledge_base.invalid_scope` and `rag.invalid_scope`.
- Limits not in the spec: a rag tool name is at most 40 characters (`[a-z0-9_-]`), a KB description at most 500 characters, a filter list at most 20 values of at most 200 characters, the admin test search `limit` at most 20.
- Round-robin order is by KB name, so results are deterministic.
- Embedding calls are one text at a time; no caching in this spec (deferred).
- `ToolAuditEntry.SourceCount` is a new nullable column.
- `Native` becomes `Builtin` in PR 0 (decided in review on 2026-10-17); `Rag` is added as a third value in PR 5.
- Sampling reads the first 20 points returned by `scroll` (not a random sample).
- The test-only dependency `Testcontainers.Qdrant` (or a generic Qdrant container) and the new `tools/Quorum.SampleKnowledgeBase` project, referenced by the integration tests and by nothing in the product.
